Unobservable parallelism

simplicity vs predictability:
Flows design, multiple methods for something that looks samy.
-two kinds of forEach
-errors for 'unpredictable' shapes, with ways to suppress them.
Clearly 'simpler' to not expose any of those problems to the user.

On a rare corner case:
Simple->hide the existence of the corner case until it manifests
Predictable->scream the existence of the corner care even lauder since it is rare.


Predictable != can never observe the OS details.
But... it needs to be only doing it in clearly designed situations.
OC should be designed to make propagation of those observability skills very obvious.
Most code should not be able to probe if it is running on win or on linux, for example.

The importance of naming conventions

Functional programming, defensive vs offensive mindset
compare
zip function
vs
Floating point Nan behaviour.
They are both defensive. They are both non predictable.
Predictable failure is better then simpler formalisation of the behaviour.

Predictable behaviour is not behaviour that is mathematically simple.
It is behaviour that is mathematically USEFUL. Other code logic relying on that behaviour can be simple while propagating predictable behaviour to its users. This seems to be an inductive argument across chains of API->Client.


Predictability  != predictably works.
If you want predictably working software you will have
software that neither works, nor is predictable.

What we can have is software that predictably either works or explains why it can not.
Then, with slow painful iterations we can grow the set of situations where the code works.
Predictability is a compositional property: putting together predictable code you should get more predictable code
Crucially, growing the set of working situations is not compositional.
